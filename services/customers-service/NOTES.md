# customers-service: learning notes

What each file generated by Spring Initializr does, and what happens when the project builds.

## Project files

| File | What it is for |
| --- | --- |
| `pom.xml` | Maven's project file: name, Java version, dependencies and build plugins. The heart of the build. |
| `mvnw`, `mvnw.cmd` | Maven Wrapper scripts (Unix and Windows). They download the exact Maven version the project expects, so anyone can build without installing Maven. Always use `./mvnw`, not `mvn`. |
| `.mvn/wrapper/maven-wrapper.properties` | Tells the wrapper which Maven version to download and from where. |
| `.gitignore`, `.gitattributes` | Ignore build output (`target/`) and IDE files; keep `mvnw` with Unix line endings so it runs on Linux and macOS. |
| `HELP.md` | Links to the docs of the chosen dependencies. Safe to delete. |
| `target/` | Build output (compiled classes, test reports, the final jar). Generated, never committed. |

## Inside `pom.xml`

- **`<parent>spring-boot-starter-parent</parent>`**: inherits sensible defaults and a curated list of library versions that work together. That is why most dependencies have no `<version>`.
- **`spring-boot-starter-webmvc`** (named `spring-boot-starter-web` before Spring Boot 4): a *starter*, a bundle of dependencies for one purpose. Brings Spring MVC, Jackson (JSON) and an embedded Tomcat server.
- **`spring-boot-devtools`** (`optional`, `runtime`): restarts the app when compiled classes change. Disabled automatically when running the packaged jar.
- **`spring-boot-starter-webmvc-test`** (`test` scope; `spring-boot-starter-test` before Spring Boot 4): JUnit 5, AssertJ, Mockito, MockMvc and Spring's test support. Only on the test classpath.
- **`spring-boot-maven-plugin`**: repackages the normal jar into an executable "fat jar" that contains all dependencies.

## Source code

| File | What it is for |
| --- | --- |
| `src/main/java/com/nexo/customers/CustomersServiceApplication.java` | Entry point. `main` calls `SpringApplication.run(...)`, which creates the `ApplicationContext`, scans for beans and starts embedded Tomcat on port 8080. |
| `@SpringBootApplication` | Shortcut for three annotations: `@Configuration` (this class can define beans), `@EnableAutoConfiguration` (configure things based on what is on the classpath, e.g. Tomcat because Spring Web is there) and `@ComponentScan` (find beans in `com.nexo.customers` and its subpackages). |
| `src/main/resources/application.yaml` | Configuration (port, app name, later the database). Only `spring.application.name` for now. |
| `src/main/resources/static/`, `templates/` | For static files and server-side HTML. Not used in a REST API; can be deleted. |
| `src/test/java/.../CustomersServiceApplicationTests.java` | `@SpringBootTest` with an empty `contextLoads()` test. It passes if the whole application context starts, which catches broken configuration early. |

Because component scanning starts at the package of the main class, every class must live in
`com.nexo.customers` or below, or Spring will not find it.

## Key question: what happens when I run `./mvnw package`?

1. The wrapper checks `~/.m2/wrapper` for the Maven version in `maven-wrapper.properties` and downloads it if missing.
2. Maven reads `pom.xml` and downloads any missing dependencies into the local repository `~/.m2/repository`.
3. Maven runs the lifecycle phases in order, up to `package`:
   - `validate`: the project is correct.
   - `compile`: `src/main/java` → `target/classes`, resources copied there too.
   - `test-compile` and `test`: compiles and runs the tests (Surefire plugin). If a test fails, the build stops and no jar is produced.
   - `package`: builds `target/customers-service-0.0.1-SNAPSHOT.jar`.
4. `spring-boot-maven-plugin` repackages that jar into an executable fat jar: my classes in `BOOT-INF/classes`, every dependency jar in `BOOT-INF/lib`, and a launcher that starts the app. The original thin jar is kept as `.jar.original`. DevTools is left out.
5. Result: `java -jar target/customers-service-0.0.1-SNAPSHOT.jar` runs the service anywhere with Java 21, no Maven or IDE needed. This is what the Docker image will run.
